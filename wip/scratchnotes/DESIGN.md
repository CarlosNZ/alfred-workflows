# ScratchNotes design

Working design for ScratchNotes: quick scratch notes, each a Markdown file, listed in Alfred and opened in their own small Alfred UI windows, like sticky notes on the desktop.

Every item is marked with its status:

- **Decided**: agreed, build to it.
- **Proposed**: the current idea, not agreed yet.
- **Open**: a question still to answer, possibly with options.
- **To test**: depends on Alfred behaviour that isn't documented; needs an experiment.

## Goals

- Any number of notes, each a plain `.md` file, in the workflow's data folder or a folder the user chooses. **Decided**
- An Alfred results list of the notes, with a preview and when each was last edited; actioning one opens it in its own window. **Decided**
- One window per note, so several notes can be open at once, arranged around the desktop like sticky notes. **Decided** (feasibility tested, see [Multiple windows](#multiple-windows))
- Notes are edited as Markdown, with a toggle between editing the source and viewing it rendered. **Decided**
- Each note has its own colour, shown in its pinned window and in the results list. **Decided**
- New notes from a keyword, from the results list, and from a Universal Action on text. **Decided**

## Storage

### Notes folder

- One `.md` file per note, in a notes folder. **Decided**
- By default the notes folder is `notes/` in the workflow's data folder (`$alfred_workflow_data/notes/`), created on first use. The data folder, not the cache, which Alfred or a cleaning app may empty; a subfolder, so the notes are kept apart from anything else the workflow stores there. Notes only go somewhere permanent and visible if the user sets the `notes_folder` preference. A configured folder must already exist and is never created, so a folder on an unmounted volume isn't recreated on the startup disk. **Decided**
- The notes are the files directly in the folder whose names end in `.md`, in any case (`.MD` too), and don't start with `.`. Subfolders, hidden files (including temporary save files) and other files are ignored. **Decided**
- When `notes_folder` changes, the notes move to the new folder without asking, so the change is seamless. **Decided**. How is in [Moving the notes folder](#moving-the-notes-folder), built in step 8 (see [Steps](#steps)).
- A configured folder that doesn't exist gives a single result, "Missing notes folder", with the folder's path as its subtitle, whether or not a move is due. Any other problem opening the folder keeps the result "Can't open the notes folder", with the reason. **Decided**

### Moving the notes folder

Built in step 8. Alfred runs nothing when a User Configuration value changes, so the move happens on the workflow's next run. **Decided** throughout, except where marked:

- **Noticing a change.** The folder the notes were last in is recorded, as an expanded path, in `$alfred_workflow_data/last-notes-folder`, which is local to each Mac. Every entry point that reads the setting (`list.js`, `new.js`, `open.js`) first compares it with the folder the setting gives now. The window scripts don't, as each window works on the folder in its bundle's context. With no record yet (the first run), the current folder is recorded and nothing moves. The record changes only once a move has finished.
- **A lock.** A move holds a lock: a folder, `$alfred_workflow_cache/move.lock/`, holding the process ID of the move. Creating a folder succeeds or fails in one step, so only one run can take the lock. A run that finds the lock held by a live process doesn't wait. It stops at once, as described under "While a move is running". A lock whose process has gone (a crash, a forced quit, a restart) is stale, and the next run takes it over and carries on with the move. A lock with no process ID in it yet is still being taken, and counts as held for 5 seconds.
- **Its own process.** The entry point that notices the change starts the move, `scripts/move.js`, as a separate background process and stops, rather than moving the notes itself. Both Script Filters have `queuemode` 2, so a keystroke stops the run in progress, which would cut a move short. Alfred sends SIGTERM to the run's whole process group, so a background child is stopped with it, even one disowned with `&!` (tested, 25 Nov 2026, with posted keystrokes; AppleScript's `search` with a new query doesn't stop the previous run, so it can't test this). A JXA script that first calls `setsid()` (`ObjC.import("unistd")`) is in a session and process group of its own, and survived. So the move is a JXA script, started in the background with its input and output on `/dev/null`, whose first act is `setsid()`. A keystroke in the moment before that stops it too, which is harmless: the next run starts the move again. zsh can't do this itself: without a terminal, `setopt monitor` fails, and macOS has no `setsid` command.
- **While a move is running**, the results list and the new-note keyword give a single result, "Moving notes…" (not actionable), with `rerun` set (0.5 s), so Alfred re-runs them and shows the notes once the move has finished. The routes with no results list (the hotkey, New note from clipboard and the Universal Action) stop without opening anything. Only a new note is lost that way, and its text is still where it came from (the clipboard or the selection), so there's no notification.
- **Pinned windows are closed first**, all of them (`pinnedNoteIds`), so none is left saving to the old folder. Each is asked to quit normally, so its `quit` event saves the note into the old folder (the folder in its bundle's context), and the move waits for its process to exit. A window still running after a few seconds is force-quit. Quitting an Alfred UI helper normally (`NSRunningApplication`'s `terminate`, run as Alfred) fires the window's `quit` event, which saves the note in Edit mode, removes its state and records its mode, and the process exits only after those writes, about 100 ms after the request (tested, 25 Nov 2026). So waiting for the process to exit is enough. In JXA, `isTerminated` never changes, as nothing runs the run loop that updates it, so the wait polls `kill(pid, 0)`. Quick views need nothing: none can be open while the configuration sheet is, and their bundles' fingerprints include the notes folder, so `list.js` rebuilds them.
- **The same folder.** The setting and the record name the same folder if, with symlinks resolved, they have the same volume and file number (`NSFileSystemNumber` and `NSFileSystemFileNumber`), so `~/notes` and `~/Notes` on a case-insensitive volume, or a symlink and the folder it points to, don't count as a change. The record is then updated to the setting's path and nothing moves.
- **The new folder is missing**: nothing is moved and the record isn't changed. The list shows "Missing notes folder" (see [Notes folder](#notes-folder)), and the move happens on the first run after the folder exists.
- **The old folder is missing** (on a volume that's no longer mounted, say): nothing is moved, and the record is updated to the new folder, which the workflow uses from then on. The notes left in the old folder can be moved by hand.
- **What moves**: every note, the files the results list shows (see [Notes folder](#notes-folder)), with its sidecar if it has one. A note without a sidecar moves too. Sidecars without a note (those of notes in the Trash) are deleted: Finder's Put Back returns a note to the old folder, outside the notes folder, so they're of no use. Other files in the old folder, its subfolders and hidden files stay where they are.
- **Into a folder that already has notes**, the sidecars go into its `.scratchnotes` folder, created if missing, beside the ones already there. A note whose ID is taken in the new folder is renamed with the next free suffix, as for a new note (`foo` becomes `foo-2`, then `foo-3`; `foo-2` becomes `foo-2-2`), keeping its extension's case, and its sidecar is renamed with it. An ID is taken there as it is for `newId`: by a note, in any extension case and Unicode normalization, or by a sidecar, even one without a note. The one exception is a note with the same text as the note of the same ID in the new folder (left by a move that was cut short, or the same note copied by hand): only one copy is kept, the one in the new folder. The old copy is deleted, and its sidecar is moved only if the note in the new folder has none.
- **Moving each note.** Each note and its sidecar are moved one at a time: the sidecar is copied, the note moved, and then the old sidecar deleted, so a move stopped at any point leaves nothing lost (a sidecar in the new folder with exactly the text of the note's own is the copy made by a move that was stopped, and doesn't count as taking its ID). Within a volume a note is renamed, and a sidecar's copy is a hard link, made in one step. Across volumes, a file is copied to a temporary hidden name in the new folder (`.scratchnotes-move-…`), renamed into place, and only then deleted from the old folder, so a move that's cut short never leaves a half-written note. The rename into place fails rather than replace a file, so a note is never overwritten. Modification times, birth times and Finder tags are kept, within a volume and across volumes (tested, on a disk image), and a copy's birth and modification times are set from the original's in case a volume doesn't keep them. Temporary files left by a move that was cut short are deleted before a move starts.
- **When a move stops part way**, cut short or failing on a file (a read-only folder, a full disk), the record isn't changed, so the next run carries on, skipping or moving what's left by the rules above. A failure is recorded in `$alfred_workflow_cache/move-failure.json` (the two folders and the reason), and the results list and the new-note keyword show it once, as a single result, "Couldn't move the notes", with the reason, without `rerun`. Showing it removes the record, so the next run (a keystroke, or opening the list again) tries the move again; retrying straight away would make the list's rerun retry for ever. `open.js` doesn't show it, and tries again. There's no check before moving: a move that stops part way is carried on, so finding out first gains nothing.
- **Finishing.** Once every note has moved, the old folder's `.scratchnotes` is removed, with any sidecars still in it, and the record is updated to the folder the move went to (not whatever the setting says by then). If the old folder was the default one, `$alfred_workflow_data/notes/`, it's removed too if nothing is left in it; it's created again if the setting is cleared. A folder of the user's own is left in place.
- **Speed**: under a second for 1,000 notes with sidecars, on one volume: about 0.7 s (`dev/test-storage.sh`). Copying the sidecars took it to 1.15 s; hard links brought it down.
- **The warning.** The `notes_folder` field's description says that changing it moves the notes and closes any pinned notes: "Where your notes are kept, one Markdown file each. Leave empty to keep them in the workflow's own data folder. Changing it moves your notes to the new folder, and closes any pinned notes." The user guide says the same (step 10).

### Filenames

- Filenames are stable IDs, never derived from the content, so a file isn't renamed while a window has it open. A note's ID is its filename without `.md`, so a file added by hand (`shopping.md`) is a note too, with its own name as its ID. **Decided**
- New notes are named for their creation time in local time, `YYYYMMDD-HHMMSS.md` (e.g. `20261120-153012.md`), with `-2`, `-3`… added if the ID is taken. Sorts by creation in Finder. An ID is taken if its note or its metadata sidecar exists (a trashed note keeps its sidecar), or if the caller says so, which lets new notes that are open but not yet saved count (see [lib.js](#libjs)). **Decided**

### Metadata

- Per-note metadata, such as the colour and creation time, is kept in a hidden JSON sidecar per note, `.scratchnotes/<id>.json` in the notes folder, rather than as YAML front matter in the note. **Decided**
  - Each `.md` stays plain Markdown, which can be moved, exported or opened in any app without a block of YAML at the top, and the editor's text is the whole file, with nothing to remove and put back.
  - Changing a note's colour doesn't rewrite the note, so it doesn't change its modification time and move it to the top of "last edited".
  - Sidecars stay with the notes when the whole folder is synced or copied, but a note moved or renamed on its own loses its metadata (it gets the default colour). Front matter was chosen first so metadata would travel with each note; with the notes in the workflow's data folder by default, that matters less than the above.
  - A hidden folder adds one hidden item to the notes folder, rather than a file per note beside each note.
- A sidecar holds a JSON object, merged on write: keys being set are replaced, keys set to null are removed, and every other key is kept as it is, including ones from other versions or tools. An unreadable sidecar, or one that isn't a JSON object, reads as empty. A sidecar is only written once there's something to store, and removed when its last key is. **Decided**
- Every note in the notes folder is used, with or without a sidecar, so `.md` files added by hand or by other apps are notes too. A note without a sidecar is given one the first time it's read or listed, recording the file's birth time as `created`. A sidecar that exists but can't be read is left alone rather than overwritten. This applies in any notes folder, including one of the user's own, so "has a sidecar" doesn't mark the notes ScratchNotes made. **Decided**
- Moving a note to the Trash leaves its sidecar in place, so a note that's put back keeps its colour. TO-DO: a sweep for sidecars whose notes have been gone a long time (each is a few hundred bytes).
- Notes from other apps may start with YAML front matter. It's left in the text, but skipped when working out the title and preview.
- Sidecar keys so far: `created`, `colour` (step 4) and `mode`, the mode (`edit` or `view`) a note's window was last in, recorded when the mode is switched and when the window closes, so the note reopens in it (see [Layout and controls](#layout-and-controls)). **Decided**. Step 7 adds `icon`, the name of the note's icon, absent for no icon (see [Note icons](#note-icons)).

```json
{
  "created": "2026-11-20T15:30:12+13:00",
  "colour": "yellow"
}
```

### Title, timestamps, empty notes

- The title is the note's first line that has any text once Markdown markers are removed: heading `#`s, `>` quotes, list bullets and numbers, task boxes, and inline emphasis, code and link syntax (a link becomes its text). Code fence lines, thematic breaks and setext underlines are skipped. "Untitled" if nothing is left. The preview is the following lines, cleaned the same way and joined: " | " before a heading, ": " after one, ", " between list items, and a space between other lines (`# Shopping` / `- milk` / `- eggs` gives "Shopping" and "milk, eggs"; `## Team meeting` / `### Decisions` / `- Ship on Friday` / `- Stand-up at 9:30` / `### Actions` / `- Release notes` gives "Team meeting" and "Decisions: Ship on Friday, Stand-up at 9:30 | Actions: Release notes"). Only `#` headings count, since a setext heading's text comes before its underline. Both are truncated on whole characters (an emoji with modifiers, a flag, or a letter with combining accents counts as one, and is never split), with "…": the title at 80 characters and the preview at 100. **Decided**
- "Created" is recorded in the note's sidecar (`created`, ISO 8601 in local time with its UTC offset) when the note is first saved, or, for a note added by hand, first read or listed (the file's birth time then), so it never changes, whatever happens to the file. "Last edited" is the file's modification time. **Decided**
- Saves are atomic, keep the file's birth time and Finder tags, and skip writing when the text hasn't changed (see [Saving](#saving)), so opening and closing a note doesn't change its "last edited". **Decided**
- A note is empty when its text is only whitespace, whatever its sidecar holds. A new note isn't written to disk until its text isn't blank. Saving blank text over an existing note writes it, so deleting everything and typing again keeps the note's file and sidecar. A note that's empty when its window closes is deleted outright with its sidecar (not through the Trash: there's nothing to recover), so abandoned new notes leave no files. **Decided**

## Colour

- Each note has a colour, stored in its metadata sidecar (see [Metadata](#metadata)). **Decided**
- Colours are a fixed, named palette, picked from a menu on a top-row button (see [Colour control](#colour-control)), and stored by name (`"colour": "yellow"`). **Decided**
  - Each name maps to its colours, defined in one place, so the palette can be re-tuned without rewriting notes.
  - The workflow ships one pre-made dot icon per colour for the results list: a circle filled with the spine colour and ringed in the control colour, so yellow and grey show on light and dark Alfred themes, drawn by `dev/make-icons.js`. **Decided**
  - A missing or unknown colour name gets the default colour (see [Configuration](#configuration)).
- The palette is Stickies' six colours, read from its asset catalogue (`/System/Applications/Stickies.app/Contents/Resources/Assets.car`, with `assetutil --info`): the note's tint, a stronger "spine" colour (Stickies' menu swatches) and a "control" colour. Dark text (`#1D1D1F`) on the tints has a contrast of 10–15:1. **Decided**

| Name | Tint | Spine | Control |
|---|---|---|---|
| `yellow` (default) | `#FEF49C` | `#FEEA3D` | `#DBC503` |
| `blue` | `#ADF4FF` | `#89F0FF` | `#24D0E9` |
| `green` | `#B2FFA1` | `#83FE83` | `#51BB51` |
| `pink` | `#FFC7C7` | `#FFB2B2` | `#F87F7F` |
| `purple` | `#B6CAFF` | `#9BB6FE` | `#7D9BEB` |
| `grey` | `#EEEEEE` | `#DADADA` | `#A8A8A8` |
  - Free choice (hex) was rejected: Alfred UI has no colour well component, so it would need `opendialog`-style workarounds or a `webkitview` (unproven), icons generated on demand, and tints derived from arbitrary hex values to stay readable.
  - TO-DO, after v1: let the palette's colours be customised (the six named colours, each with its tint, spine and control colour, rather than free choice per note). The icons are made on demand from the palette before v1 so that this needs no drawn images (see [Icons made on demand](#icons-made-on-demand)).
- The colour tints the whole of a pinned window, text area included, like a sticky note: the root view's `background` is the tint, the `textarea` has `background: null`, so it shows through it, and View mode's page has the tint as its background (see [View mode in a web view](#view-mode-in-a-web-view)). Tested inside Alfred and in a pinned window, with solid (`#FFF3B0`), translucent (`#FFCC0033`, `#FFCC0066`) and macOS (`systemYellowColor`, `yellowColor`) colours, all readable in light appearance. **Decided**
- The quick view isn't tinted: its root view has no `background` or `appearance` (they're `@pinned` in `ui/window.json`), so it takes Alfred's theme, text and buttons included, and looks like the rest of Alfred's window (checked with a dark theme). **Decided**. Its only accent of the note's colour is the colour button's dot. **Decided**. A 4pt stripe of the spine colour down the left edge was tried: in the `border` layout it only spans the middle band, between the top row and the bottom, so it looks like a quote bar; a full-height one would need another layout level. A top row in the spine colour would be heavy against a dark theme.
- A pinned note looks the same in light and dark appearance, like Apple's Stickies: its pale tint stays, and its text is always dark, set with `colour` on the `textarea` and the page's own CSS. The default text colour follows the appearance, so without this, dark mode gives white text on the pale tint, which is unreadable (tested). **Decided**
  - Only macOS's named colours adapt to the appearance by themselves; hex, `rgb()`, `hsv()` and `ui.json`'s `colours` constants are fixed. Adaptive notes would need either a light and a dark tint per colour, chosen by the script that opens the window (so an open window keeps its tint until reopened), or a translucent tint that suits both.
  - TO-DO: dark-appearance variants of the palette, in a later version.
  - Tested in dark appearance with a pale tint and `colour: "#1D1D1F"` on both: the editor and the rendered view stayed dark and readable across seven pale hues (`#FFF3B0`, `#FFD6E0`, `#D6E9FF`, `#D9F2D0`, `#E8DDF7`, `#FFE2C2`, `#E6E6E6`). The top row's buttons still switched to their dark style.
  - Simpler, and covering the buttons, caret and selection too: the root view has `appearance: "light"`, so the whole note keeps its light-appearance look, rather than setting `colour` on each component. **Decided**. Tested: a view's `appearance` applies to everything inside it, pinned and inside Alfred. A root view set to `"light"` inside a window forced to `"dark"` kept its dark text and light-style buttons; only the title bar follows the window's appearance. Inside Alfred, without it, text took Alfred's theme (white with a dark theme), unreadable on the tint.

### Colour control

**Decided**, and built in step 4:

- A borderless `circle.fill` button in the note's control colour, after the icon button at the top left (see [Layout and controls](#layout-and-controls)), opens the colour picker, a drop-down like the icon picker (see [Note icons](#note-icons)): the six colours in a row, each as its dot (`icons/<colour>.png`, the results list's, at 18 pt), with its name and shortcut as its tooltip ("Blue (⌘2)"), and the note's colour bordered, so its bezel marks it. **Decided** (25 Nov 2026). It replaced a menu like Stickies' Color menu, each colour as a heart and its name with ✓ on the note's colour, as menu items can't show a coloured dot (they take no image, and a `●` in the text takes the text colour), and three of the hearts needed macOS 13.3.
- ⌘1 to ⌘6 set the colours directly, in that order, as in Stickies, with the same action as the colour's button (an array of actions works in a shortcut too). The colour button's tooltip gives them ("Colour (⌘1–⌘6)"), and each colour's tooltip its own.
- A colour's button runs `window.js colour <name>`, which writes the sidecar (`updateMeta`) and replaces the top row's customise group (the icon and colour buttons), so the dot's colour follows, and the colour picker, which marks the new colour and comes back hidden, so choosing closes it (the icon picker and the catcher are hidden too); it also updates the colour in the bundle's `context.json`, so what the window's scripts give it later matches (the page's tint, on a switch to View). In a pinned window the button's action is an array that first sends an `update` of the root view's `background`, so the tint changes at once, without waiting for the script; in View the page covers the window, so the script also reloads the page with the new tint.
- No right-click menu: the `textarea` and the web view keep their own menus, so it would only work in the margins.

Alfred UI's menus aren't documented. Found in its framework (`AUIMenu`, `AUIActionJSONProcessorPopupMenu`) and tested on 25 Nov 2026, in a standalone window and in the quick view:

- `{"popupmenu": {"src": "<component id>", "menu": [items]}}` is an action that pops up a menu at that component: over it, at its top-left corner, with the first item under the pointer (not the checked one). A script can print it too.
- An item is `{"text", "state", "action", "submenu"}`, or `{"type": "separator"}`. `"state": "on"` shows ✓ and `"mixed"` shows –. An item without an `action` is greyed out. Items take no image and no key equivalent, so a swatch can only be an emoji in the text: a `●` takes the text colour (white in a dark menu).
- The `action` is any Alfred UI action: a `script` (its `args` expand `{value:…}`), `json` (an `update` of the background from an item worked), or an array of actions, run in order. Nothing says which item was chosen, so each item's action carries its colour.
- The `menu` key, which every component takes, is its right-click menu (`setMenu:`). It works on views and buttons, and a click on a child without its own menu shows its parent's. A `textarea` or `markdownarea` keeps its standard text menu.
- The menu takes the appearance of the view it opens from: light in a pinned note (its root view has `appearance: "light"`), Alfred's theme in the quick view.
- In the quick view, a menu opens and its items' actions run without Alfred closing. Esc with a menu open closes only the menu; a second Esc closes Alfred. ⌘1 and a ⌘K shortcut that opens the menu both worked inside Alfred, though Alfred uses ⌘1–⌘9 for its results.

### Note icons

A note can have an icon, chosen from 20, or none. A note's icon is shown on its result in the note's colour, in place of the colour dot, in its window's top row in the buttons' own colour, and as a pinned window's app icon. Step 7 (see [Steps](#steps)). The design is below; found first (25 Nov 2026, with a prototype outside the workflow):

- The icons would come from [Lucide](https://lucide.dev) (ISC licence: ship its `LICENSE` with them): 2,416 outline SVGs on a 24-point grid, drawn with `stroke="currentColor"`. All of these exist: `sticky-note`, `shopping-cart`, `lightbulb`, `list-todo`, `book-open`, `briefcase`, `calendar`, `phone`, `house`, `heart`, `star`, `flag`, `bookmark`, `code`, `music`, `plane`, `utensils`, `dollar-sign`, `key-round`, `gift`. Tabler and Phosphor (MIT) are alternatives. SF Symbols aren't: a Script Filter's `icon` only takes a file's path, a file's icon or a file type's, and Apple's licence doesn't allow shipping symbols as images.
- Colouring them is simple. NSImage reads an SVG in JXA once its `currentColor` is replaced with a hex colour, and draws it into a bitmap as `dev/make-icons.js` does. The prototype drew all 120 (20 icons × 6 colours, at 128 px) in about 0.2 s. As the palette is fixed, `dev/make-icons.js` can draw them all and the workflow can ship them (under 1 MB), so nothing is drawn at run time and nothing depends on which macOS versions read SVG.
- Style: a badge, the icon in dark text colour (`#1D1D1F`) on a rounded square of the tint, ringed in the control colour. It reads well on light and dark Alfred themes, and looks like a small sticky note. The icon alone in the control colour is faint on a light theme in yellow and grey.
- Choosing an icon: menu items take no image (see [Colour control](#colour-control)), so a menu could only list names. But a button shows a PNG, so a grid of icons in the window works (below).

A button's `image` takes a PNG file. Tested on 25 Nov 2026 with a throwaway bundle in a pinned window (a temporary External Trigger to the pinned Alfred UI object, removed afterwards), checked with a screenshot:

- `"image": { "type": "file", "src": "<path>", "size": { "width": 24, "height": 24 } }` on a borderless button shows the image at that size. Without `size` it's drawn at its own size (a 128 px image came out about 80 pt across), so every file image needs one. On a symbol, `size` has no effect: its size follows the button's `font`.
- A bordered button draws its grey bezel behind the image, which can mark the chosen icon.
- A relative `src` is taken from the bundle's folder. The note bundles are in the cache, so their images have absolute paths into the workflow folder.
- `"template": true` with `contenttintcolour` didn't tint a file image; it kept its own colours. The framework explains why: `AUIImage` reads only `type`, `src` and `size`, and its `loadImageForUI:` loads a `file` image with `initWithContentsOfFile:` and never makes it a template (`setTemplate:` is only for symbols, before macOS 13). NSImage doesn't make a file whose name ends in `Template` a template either (checked in JXA). So a file image can't take a button's `contenttintcolour`, or follow the appearance: every colour an icon is shown in is drawn ahead of time.
- The buttons' colour, `secondaryLabelColor`, is black at 49.8% alpha in light appearance and white at 54.9% in dark (read in JXA, macOS 27).
- An `imageview` shows a file image too (Now Playing's artwork does), but gets no `clicked` (see Now Playing's `DEVELOPMENT.md`), so the grid is buttons.
- In the framework, `AUIButton` and `AUIImageView` share one image class, `AUIImage`, which reads the `type`, `src` and `size`. The framework also has a `grid` layout (`AUIGridLayout`), untested; rows of `inline` views are used instead.
- Clicking a button with a file image wasn't tried (no clicks were sent); it's the same button as the symbol ones.

#### Design

**Decided** (25 Nov 2026), except where marked, and to be refined as it's seen in use. Built in step 7:

- **No icon**: a note has no icon until one is chosen, and there's no default icon. A note without one shows its colour's dot on its result, and the ScratchNotes app icon when pinned. Its window's icon button shows a placeholder (below).
- **The set**: 20 Lucide icons, in this order (the grid's), each with a label for its tooltip and accessibility label: `sticky-note` (Note), `list-todo` (To-do), `shopping-cart` (Shopping), `lightbulb` (Idea), `book-open` (Reading), `bookmark` (Bookmark), `briefcase` (Work), `calendar` (Calendar), `phone` (Call), `users` (People), `house` (Home), `utensils` (Food), `plane` (Travel), `gift` (Gift), `wallet` (Money), `code` (Code), `music` (Music), `heart` (Heart), `star` (Star), `flag` (Flag). Two changes from the prototype's list: `wallet` in place of `dollar-sign` (not tied to one currency), and `users` (meetings, people) in place of `key-round`, which suggests keeping passwords in plain-text notes. The set is a first version, to be refined.

#### Icons made on demand

**Proposed** (25 Nov 2026), to build before v1 (step 9 in [Steps](#steps)). Two reasons: the palette is to become customisable (see [Colour](#colour)), which pre-drawn images can't follow, and macOS 12 can't read SVG (see [Note icons](#note-icons)), so the icons must never reach a window there.

- **No drawn icons in the bundle.** The workflow ships Lucide's SVGs as they are, in `vendor/lucide/` with its `LICENSE` and a `VERSION` file (moved from `dev/lucide/`, since they're needed at run time, as markdown-it is), and nothing drawn from them: `icons/lucide/` and the colour dots, `icons/<colour>.png`, go, and `dev/make-icons.js` with them. **Open**: the drop-downs' shadows don't depend on the palette, so they can stay drawn ahead of time, or be drawn at run time too, so the bundle has no drawn images at all.
- **Coloured dots.**
  - In the window, the colour button and the colour picker show the `circle.fill` symbol tinted with each colour's control colour (`contenttintcolour`), as the colour button already does, so they need no files and work on macOS 12. The picker's dots lose the ring of the current images, which helps pale colours stand out, so they use the stronger control colour rather than the spine colour.
  - In the results list, a result's icon has to be a file, and can't be a symbol, so a note without an icon gets a PNG dot drawn on demand with AppKit (a filled circle with a ring, as `make-icons.js` draws them now, which works on macOS 12) and cached. Not drawn from the SF Symbol, whose licence doesn't allow using symbols as images elsewhere.
- **Lucide icons, as SVG text, on demand.**
  - Each is made when it's needed, into the cache: a badge (an icon on its colour's square) for a result and a pinned window's app icon, and a glyph (an icon in the buttons' colour, light or dark) for the window. Making one is filling in Lucide's SVG text, which takes microseconds and needs no drawing code.
  - One function in `lib.js` returns an icon's file, making it first if it's missing, and everything that writes an icon's path (a result, a window's `ui.json`, the app icon) goes through it, so a path never names a file that isn't there. Making a badge when an icon is chosen in the picker covers the common case; the rule also covers a cache that Alfred or a cleaning app has emptied, a palette that has changed, and a note given its icon on another Mac. If a file can't be made, the caller falls back to the dot or a symbol rather than name a missing file.
  - The picker shows every icon at once, so the glyphs (about 50: the icons, light and dark) are all made the first time any is needed. They don't depend on the palette.
  - Each file is named by a hash of everything it's made from (its style, its colours, and the Lucide version), so a changed palette colour gets new files rather than stale ones. Old ones are swept now and then.
- **macOS 12: no icons.** The icon button, the icon picker and ⌘I are left out of the window, results show the dot, and a pinned window keeps the ScratchNotes app icon.
  - A note's `icon` is dropped where the rest of the code reads it: `noteIcon(meta)` gives no icon on macOS 12, so it's never passed along to be drawn. Not in the sidecar's own read, which `updateMeta` merges changes into: dropping it there would write the sidecar back without it on the next colour change. So the sidecar keeps it, for a notes folder that's also used on a Mac with macOS 13 or later.
  - Whether the Mac can use icons is a check of the macOS version (13 or later), which needs only Foundation, so it costs nothing; asking NSImage to read a small SVG would be more exact, but loading AppKit adds about 10 ms to each run. It's part of the quick bundles' fingerprint, so a Mac upgraded from 12 to 13 rebuilds them once.
- **The action buttons on macOS 12** (**Open**, to be decided): Edit / View and Pin are Lucide glyphs, so without a fallback every window would still fail on macOS 12, icon or not. The obvious fallback is the SF Symbols they were before step 7 (`eye`, `pencil`, `pin`), which take the buttons' colour by themselves and work on 12, though they'd differ in style from macOS 13's.
- **To test**: whether a window whose `ui.json` names an image file that doesn't exist is rejected the same way on macOS 13 and later (likely, as NSImage returns nil for a missing file as for an unreadable one), with a throwaway bundle opened through a temporary trigger, no clicks needed. If it is, making files whenever they're named matters on every version, not only on 12.
- Considered and not chosen for now:
  - Pre-drawn PNGs of every icon in every colour: they work on macOS 12, but can't follow a customisable palette.
  - Drawing the icons as PNGs at run time, to keep icons on macOS 12: either Lucide icons shipped as black masks and recoloured with AppKit (tried: 13 ms a badge, plus about 10 ms to load AppKit), or Lucide's SVGs drawn with AppKit through [svgpath](https://github.com/fontello/svgpath) (MIT, 43 KB, no dependencies), which turns any SVG path into plain moves, lines and curves (arcs included), leaving 50–60 lines of drawing code. Kept in reserve if icons are wanted on macOS 12.
  - Other SVG renderers: canvg draws onto a browser canvas, which JXA doesn't have; resvg-wasm (2.5 MB) needs promises, which `osascript` doesn't run; sharp is a Node.js module with compiled libraries, so it would need Node and signed binaries.

## Alfred results list

A Script Filter on a keyword (`scratch` by default, configurable), run by `scripts/list.js`. **Decided** throughout, except where marked:

- One result per note, sorted by last edited, newest first. No result has a `uid`, so Alfred keeps this order. With each note's ID as its `uid`, Alfred's learning moved notes chosen often above New note and above more recently edited notes (tested). `skipknowledge: true` stops Alfred recording what's chosen, but it still sorts by entries recorded before the flag was added (tested): they're the rows of the `knowledge` table in `~/Library/Application Support/Alfred/Databases/knowledge.alfdb` whose `item` is `<Script Filter object uid>.<item uid>`. Without uids those entries can't match, so a Mac that ran an earlier build needs no clean-up. A `uid` would only be worth adding with `rerun`, where it keeps the selection on the same item (as in Now Playing and World Clock), and would then need `skipknowledge: true` and those old entries deleted.
- While `list.js` runs, before the first results arrive, the keyword's result says "Loading notes..." (the Script Filter's "Please Wait" subtext, `runningsubtext`). A run usually takes 0.1–0.2 s, but rebuilding every quick bundle, once after a workflow update or a change of setting, took about 1.5 s with 300 notes (see [Seamless quick views](#seamless-quick-views)). While typing, Alfred keeps the previous results up, so it doesn't show then. **Decided**
- Title: the note's title. Subtitle: when it was last edited and its preview, e.g. `Edited 3h ago · milk, eggs, flour…`. The time is "just now", minutes, hours or days ago ("5m ago", "3h ago", "2d ago"), and after a week the date in the Mac's format ("12 Nov", with the year if it isn't this year). A note that's pinned has "Pinned · " in front.
- Icon: the note's colour's dot (`icons/<colour>.png`). New note has no icon of its own until the workflow has one (step 10). From step 7, a note with an icon shows it in its colour in place of the dot (see [Note icons](#note-icons)).
- Typing searches the whole note, not just the title: every word of the query must appear somewhere in the note, in any order, ignoring case and accents ("cafe" finds "Café"). `list.js` does the matching itself, rather than leaving it to Alfred (`alfredfiltersresults` is off), since it has to know when nothing matches. It reruns on every keystroke, reading every note (about 115 ms for 300 notes, plus `osascript`'s startup), and Alfred stops the previous run when a new one starts (`queuemode` 2).
- A **New note** result, at the top with no query. With a query that matches nothing, it's the only result, **New note: \<query>**, creating a note with that text. ↩ and ⌘↩ on it behave as they do on a note, as closely as possible: ↩ opens the new note in a quick view, ⌘↩ pins it. Its arg is the bundle of a quick view of a new note with that text (see [Quick notes and pinned notes](#quick-notes-and-pinned-notes)); ⌘'s arg is the text itself (empty for a blank note), with the variable `new` set to `1`, so `open.js` knows it isn't a note's ID. ⌥ and ⌃ do nothing on it (`valid: false`): their actions take a note's ID or path, and the query would otherwise reach them as one.
- ⌘C copies the note's text and ⌘L shows it in Large Type. → shows Alfred's file actions for the note's file (the item's `action`).
- Modifiers on a note:
  - ↩ opens it in a quick view inside Alfred, or, if it's already pinned, brings its window to the front (see [Quick notes and pinned notes](#quick-notes-and-pinned-notes)). **Decided**
  - ⌘↩ pins it: opens it as its own window on the desktop, or brings that window to the front if it's already pinned. **Decided**
  - ⌥↩ moves it to the Trash, through Finder so "Put Back" works, without asking first, and shows a notification naming the note. If the note is pinned, its window is closed first (see [Changes made elsewhere](#changes-made-elsewhere)). **Decided**
  - ⌃↩ reveals it in Finder.
  - ⇧ / ⌘Y Quick Looks it (`quicklookurl` is the file).
- Creating a note from the clipboard is a result of the new-note keyword rather than a key here, since ⌘↩ on New note pins it and ⌥↩, unused on New note, moves a note to the Trash, so one slip would trash a note (see [Creating notes](#creating-notes)). **Decided**

## Creating notes

**Decided**, and built in step 6. A new note is created the same way by every route: it opens before it's saved, with its starting text, and is saved when its window saves (after a pause in typing, on a switch to View, on Pin, or on closing), as New note in the results list does. Text from elsewhere isn't saved first: even a quick view opened while Alfred's window is hidden fires `quit` with its text, so the text is only lost if the window's process crashes.

- **The new-note keyword** (`snn` by default, the `keyword_new` field), a Script Filter run by `scripts/new.js`, with optional text. Its results behave exactly as New note in the results list does (`newNoteResult` in `lib.js`): ↩ opens the new note in a quick view, seamlessly (the Script Filter connects straight to the quick view's Alfred UI object, with a bundle `new.js` writes first), and ⌘↩ pins it. `snn buy milk` gives one result, **New note: buy milk**, whether or not a note already matches (unlike the results list, which only offers New note when nothing matches). `snn` alone gives **New note**, and then **New note from clipboard** when the clipboard has text, with that text on one line as its subtitle.
- **From the clipboard**: that second result, starting the note with the clipboard's plain text exactly as copied. It's offered only when the clipboard has plain text that isn't only whitespace (rich text gives its plain version; an image gives nothing), and not when it also holds files copied in Finder (whose names come as text too), or text marked concealed or transient (`org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType`), such as a password manager's, which Alfred's clipboard history leaves out too (`clipboardText` in `lib.js`). The two new notes get their own IDs and bundles (the second has `-2`).
- **A Universal Action**, "New ScratchNote", on text and URLs (so a selected link offers it too), not files: Universal Action → Run Script (`new=1 ./scripts/open.js quick "$1"`) → the quick view's Alfred UI object. It covers the macOS selection, through Alfred's Universal Action hotkey, and items in Alfred's clipboard history. It takes one item (`acceptsmulti` off). The quick view opens and stays open, since Alfred's window is showing while an action is chosen (tested by hand, 25 Nov 2026, on a selection in another app and on a clipboard history item); with a Run Script in between, Alfred hides its window and fades the view in, which is fine here, where a different view is expected.
- **An optional hotkey** for a new blank note, unset by default (the user assigns it in the workflow): Hotkey (no argument) → Arg and Vars (an empty arg and `new` = `1`) → the pin route (`open.js pin`). A quick view only works while Alfred's window is showing (tested), so a hotkey from another app opens the new note pinned.

- View mode is a `webkitview` rendering the note with markdown-it, with task boxes that can be ticked (see [View mode in a web view](#view-mode-in-a-web-view)). **Decided**, and built in step 5.
  - It was first a `markdownarea`, which renders with Alfred's own Markdown renderer (headings, lists, code blocks, tables, block quotes, images, links). It's display-only. Tables, inline code, bold and italic render; raw HTML (e.g. `<b>Hello</b>`) doesn't, and neither do task boxes: `- [ ]` and `- [x]` show their brackets as text (tested in step 3). Its default spacing is very loose, with a wide gap between the wrapped lines of a paragraph. It has four spacing keys, not in Alfred's docs (found in its framework, and tested): `linespacing`, `paragraphspacing`, `listspacing` and `lineheightmultiple`; `linespacing: 0`, `paragraphspacing: 6` and `listspacing: 2` suited notes, and `lineheightmultiple` below 1 misplaces list bullets. Heading sizes and bullet style can't be changed.
- Both modes are in the window all the time, in one full-window `stack`: the web view, the `textarea` over it, the icon picker (a drop-down, hidden until opened; see [Note icons](#note-icons)), and the top row's two groups of buttons over the top corners. The Edit / View switch is an `update`: to Edit, it fades the web view out and shows the `textarea` with the saved text; to View, it saves the text, hides the `textarea` and reloads the page with the note. The text goes through the save file both ways. See [View mode in a web view](#view-mode-in-a-web-view). **Decided**, and built in step 5. Step 3's switch was a `replace` of the content view, as Now Playing does, swapping a `textarea` and a `markdownarea`, since a hidden component still takes up space (Alfred's docs say so); a `stack` layout layers its components, so that doesn't matter there.

### View mode in a web view

View mode renders in a `webkitview`, so that Markdown renders fully (task lists included) and ticking a task's box in View mode ticks it in the note. **Decided**, and built in step 5 (see [Steps](#steps)). It has to work as people expect from other Markdown apps, so the cheaper routes were rejected: swapping `- [ ]` for ☐ in the `markdownarea` (display only); a `checkbox` component per task among `markdownarea` blocks (plain-text labels, selection stops at each block, unknown scrolling); and custom-scheme links in the `markdownarea` (it sends no click events, and its `urischemes` key only sets which link schemes are clickable, so a click goes to macOS and the window can't be told to change).

The renderer is [markdown-it](https://github.com/markdown-it/markdown-it) (MIT): CommonMark, with tables and strikethrough built in, raw HTML escaped by default (so a note can't run script in the page), and one file to vendor (`dist/browser/markdown-it.umd.min.js`, 100 KB, the global `markdownit`; 15.0.3, in `vendor/markdown-it/` with its `LICENSE` and a `VERSION` file). It records each block's source lines (`token.map`), so a task's box can carry the line it came from. Task lists need a core rule of our own (`noteTaskRule` in `ui/view.js`, after `inline`): a list item whose paragraph starts with `[ ] ` or `[x] ` gets an `<input type="checkbox" data-line="N">`. The `markdown-it-task-lists` plugin (ISC) is unmaintained since 2022 and doesn't record lines. marked has task lists built in but no source positions; micromark / remark have positions but are many ES modules to bundle. markdown-it also runs in JXA (12 ms to load, 9 ms to render a note), but rendering ahead of time doesn't make the page appear any sooner (see below), so the page renders the note itself.

The look, **Decided** (25 Nov 2026, from a prototype in Alfred):

- The web view starts at `opacity: 0` and is shown once the page has drawn: two animation frames after rendering, the page changes its fragment to `#ready-…`, and the `changed` action sets the web view's `opacity`. Shown any sooner, WebKit's own fill shows before the note: on the web view's `launched` event, or one frame after rendering, a pinned window showed a white block for about 120 ms. Measured from the page starting to load to the web view being shown: 70–180 ms in a quick view, 190–260 ms in a pinned window. The note just appears, a moment after the window, with no flash.
- In a pinned window the page's background is the note's tint and its text dark, like the window's.
- In the quick view the web view fills the whole of Alfred's window: the root view has a `stack` layout, the web view `stretch: both`, and the top row's buttons lie over its top-right corner (`position: topright`, last in the stack). The page has its own margins, and a bar of its background colour along the top, under the buttons, so scrolled text doesn't run under them. A panel inset in the window, as the `markdownarea` is, leaves a frame of Alfred's background around a panel that can't match it.
- In a pinned window the page starts below the top row (28pt down), on the window's tint, rather than under the transparent title bar: a web view takes the mouse, so a full-window one stopped the window being dragged by its title bar (it could still be resized). The strip above the page is the root view's background, which drags the window (`movablebybackground`). In Edit the hidden web view is still under the `textarea`'s margins, so only that strip drags the window. **Decided** (tested by hand, 25 Nov 2026).
- The quick view's colour comes from Alfred's theme background, `alfred_theme_background` (`rgba(r,g,b,a)`), which `list.js` gets as a Script Filter and writes into a stylesheet the pages load, so a change of theme rebuilds no bundles. The panel is the theme's colour over the appearance's base at its alpha, *a* × theme + (1 − *a*) × base (base `#1E1E1E` in dark appearance, white in light), and the web view's final opacity is *a*, but no lower than 0.8. So a solid theme (alpha 1) is matched exactly, at full opacity with the system's text colours. Below full opacity the text fades with the view, so it's drawn at 0.85 ÷ opacity (the label colour's alpha, at most 1), with brighter links, to land at its normal strength. A translucent theme's blur can only be imitated like this until Alfred can make a web view transparent (see [Alfred requests](../../Alfred%20requests.md#alfred-ui-a-transparent-background-for-a-web-view)): with a theme of `rgba(40,161,250,0.05)` the panel is near-black at 80%, a little darker and less translucent than Alfred's own background.

The mechanics, **Decided**, and built in step 5 (they follow the prototype, except where noted):

- The page is `view.html` in the note's bundle, written with the bundle from `ui/view.html` with `ui/view.js` inlined (so a changed script is never read from WebKit's cache), by `notePageHtml` in `lib.js`. It loads markdown-it from the workflow folder by its absolute `file://` path, a quick view's theme stylesheet the same way (with a `?t=` that changes every time, so a changed theme is never cached), and the note from `note.js` beside it (`window.NOTE = "…"`, and `window.NOTE_TINT`, a pinned page's colour), as `note.js?v=<version>` (see below for why). The note's text never passes through `ui.json`, so it needs no escaping for Alfred's placeholders (see [Placeholders in a note's text](#placeholders-in-a-notes-text)), and the quick bundles' fingerprints already cover it. A window that opens in Edit gets `NOTE = null`, so its page draws nothing and sends no `#ready` until the first switch to View reloads it with the note. Its empty page may still draw behind the `textarea` (an opacity of 0 set before the first draw may not hold); nothing showed there in testing by hand, so the web view isn't also hidden (`hidden: true`), which would be the fix if a panel ever shows.
- The page tells the workflow about a click by changing its fragment, `#t-<line>-<x|o>-<counter>` (the counter makes each change distinct), and that it has drawn, `#ready-<opacity>-<counter>`, with the opacity to show it at (1 when pinned; in a quick view the theme stylesheet's `--opacity`). The `changed` action is `scripts/changed.sh`, a short zsh script, since Alfred waits for it (in a quick view, in its own process) and it runs on every change of the URL, including the page starting to load: it answers `#ready` with an `update` of the web view's `opacity`, unless the window's state says Edit, passes `#t-` on to `window.js tick`, and ignores everything else. The state check came from a test by hand in which View and Edit showed at once, laid over each other, which couldn't be reproduced: most likely a page finished loading (after opening in View, a switch to View or a tick) after a quick ⌘E had faded it out, and its `#ready` showed it again. The state file is read with a zsh builtin; with no state yet, the window has just opened in View. An `osascript` started on every change held the page back by about 80 ms.
- `window.js tick` ticks the box only if the note's text still has the hash the page was built from (`textHash` in the bundle's `context.json`, updated whenever the page is given a text, by `writeNotePage`) and the line is still a task box in the other state (`toggleNoteTask` in `lib.js`). Otherwise it rewrites `note.js` and reloads the page with the note as it is now, with an `update` of the `src` to `file://<bundle>/view.html?v=<version>`. The version is the hash of `note.js` and the time, so every reload has a new URL, even with the same text (the page reloads whether or not the text has changed, and doesn't depend on whether an `update` to the same URL reloads). The page keeps its scroll position across the reload in `sessionStorage`. Tested: a tick takes about 5 ms in the script; changing the note on disk and then clicking a box reloaded the page with the changed note, at the same scroll position, about 100 ms later.
- A task's line is a list item whose text starts with `[ ] ` or `[x] `, with any indent, bullet or number, and `>` quote markers in front.
- The web view stays in the window for its whole life, rather than the switch replacing the content (each new web view takes 100–250 ms to show anything). The content is a `stack` of the web view, in a view of its own that holds the ↩ shortcut, and the `textarea` over it. To Edit, the switch fills and shows the `textarea` (`hidden: false`, `focus: true`) and fades the web view out (`opacity: 0`); to View, it saves the text, hides the `textarea` and reloads the web view with the note, which `changed` shows once the page has drawn. The toggle button's symbol, tooltip and accessibility label change with the same `update`. Both modes, in both forms, have this layout (`ui/content.json`), with the buttons over the top-right corner, so they don't move when the mode changes; in a pinned window the web view starts below the top row (see the look, above). Tested in a quick view on 25 Nov 2026: from the switch script to the note being shown took 38–66 ms (plus the script's `osascript` start-up, about 75 ms); after a switch to Edit the caret is at the end of the text, ready to type; and ↩ in the `textarea` types a new line, though the ↩ shortcut's view is still in the window. Re-rendering in place without a reload, with the note in the URL's fragment (`#n-<encoded text>`, which `hashchange` picks up), took 27–54 ms, too little difference to see, so the reload is used: a refused tick needs it anyway, and it keeps the note out of every later `changed`.

What the `webkitview` does, found in its framework (`AUIWebKitView`) and tested on 25 Nov 2026: first in a standalone window, then inside Alfred with a translucent dark theme and a solid light one, with a throwaway note, real and posted clicks and keys, and screen recordings at 60 fps.

- Its keys: `src`, `openlinksexternally` (a boolean, or a regular expression for the links to open in the browser) and `text`. A `src` that names an existing file in the bundle (`"src": "view.html"`) loads as a `file://` URL; any other `src` without a scheme gets `https://` put in front. `text` is a page's HTML, loaded with `loadHTMLString:baseURL:`, but its page can't load local scripts and sends no `changed`, so it's no use here. It also has the action functions `back`, `forward` and `reload` (`runActionFunction:`), not tried. It doesn't read `background`.
- Its value is `{value:<id>.src}`, the page's current URL. It sends `changed` whenever that URL changes, including a change of only the fragment, from `location.hash` or `history.replaceState`, and as the page starts to load. It also sends `preload` and `launched` as the page loads. Real clicks on task boxes each sent one `changed` with the right line and state.
- A script's `update` of the `src` reloads the page. It must be an absolute `file://` URL: a relative `view.html?v=2` became `https://view.html/?v=2`, which failed to load, and the web view went back to the previous URL and sent `changed` again, so a script that answers every `changed` with an `update` loops.
- A page can load scripts from any folder by an absolute `file://` URL, or through a symlink, but `XMLHttpRequest` and `fetch` fail, even for a file beside it, so the note has to come as a script.
- WebKit keeps a page's scripts: a reload with a new `?v=` on the page still ran the old `note.js` until its own URL changed too (`note.js?v=<hash>`). A new web view (the next quick view) reads them afresh.
- It's opaque. WebKit paints a fill under the page, `#1E1E1E` in dark appearance and white in light, and `AUIWebKitView` never turns it off (`drawsBackground`): a transparent CSS background shows the fill, and `"background": null` makes no difference. Before the page first draws, a new web view shows only that fill, for 130–200 ms, however little the page does: it draws within 2–9 ms of starting to load, and a page rendered ahead of time, by `src` or `text`, was no sooner. Showing a `markdownarea` first and the web view once it had loaded still blanked for 2–3 frames, and the text jumped: a hidden web view doesn't draw.
- Every component takes `opacity` (0–1, the view's alpha; undocumented, in `AUIFactory`). On a web view it fades the whole page, text included. An opacity set before the page first draws is lost: one in `ui.json`, or set by an `update` on `launched`, left the web view opaque, though opacity 0 still hides the fill until the first draw. An `update` after the page has drawn holds.
- The root view's shortcuts (⌘E, ↩, ⌘1) run on the first press, whether or not the page has keyboard focus, unlike the `markdownarea` of step 3, where the first ↩ after a click only moves the focus (see [Layout and controls](#layout-and-controls)). After a click in it, the page has the focus: ↓ and Home scroll it.
- Text can be selected by dragging or ⌘A, and ⌘C copies it as shown (task boxes without their `[ ]`). The scroll wheel scrolls it, with an overlay scroller.
- With `openlinksexternally: true`, a link opens in the default browser and the page stays where it is. A quick view closes as the browser comes forward, as Alfred does whenever another app does.
- The page takes the appearance Alfred gives its window (`prefers-color-scheme`, and colours such as `-apple-system-label`): dark with a dark theme, inside Alfred.

### Layout and controls

- A slim top row (24pt) of borderless buttons, level with a pinned window's traffic lights, in two groups: the note's own look at the left, the icon button (step 7, see [Note icons](#note-icons)) and the colour button (step 4, see [Colour control](#colour-control)), after a pinned window's traffic lights (82 pt in); and the actions at the right, the Edit / View toggle (`eye` in Edit, to switch to View; `pencil` in View, to switch to Edit) and, in the quick view only, Pin (`pin`). Each has a tooltip naming its key. The groups are separate components (`customise` and `actions`, from `ui/customise.json` and `ui/actions.json`), not one full-width row, since a view laid over the note would take its clicks. Measured from a screenshot of a pinned window (25 Nov 2026), the buttons' centres were 2 pt above the traffic lights', so the actions are 8 pt down; the customise group is 6 pt down, as its 20 pt icon makes it 4 pt taller than the actions, and its buttons are centred in it. These values are in `NOTE_WINDOW_LAYOUT` in `lib.js`, to tune by hand (see [Note icons](#note-icons)). The rest of the window is the note. **Decided** (the two groups from 25 Nov 2026). Their icons are Lucide glyphs (see [Note icons](#note-icons)); they were SF Symbols before step 7.
- ⌘E toggles Edit / View, Esc closes the window, and ⌘P pins the quick view. All three work inside Alfred as well as pinned (tested), apart from Esc inside Alfred, which Alfred handles itself by closing (the quick view's `quit` still runs). **Decided**
- ↩ in View switches to Edit, and ⌘↩ in Edit "submits": it saves and switches to View (`window.js view`, which does nothing in View). This is Jupyter's convention for Markdown cells (↩ to edit, ⇧↩ or ⌃↩ to render). Both work inside Alfred as well as pinned (tested, 25 Nov 2026). **Decided**
  - The ↩ shortcut is on the view that holds the web view (`page` in `ui/content.json`), not the root, so it only runs while the focus is in View's side of the window: in Edit, ↩ in the `textarea` types a new line, though that view is still in the window (tested). Shortcuts on an inner view work (tested).
  - With the `markdownarea` of step 3, the first ↩ after a click in its text only took the focus off it, and a second ↩ switched (tested); `focusable: false` doesn't apply to a `markdownarea`. The web view has no such problem (see [View mode in a web view](#view-mode-in-a-web-view)).
  - Double-click to edit, as in Jupyter or VS Code's preview, isn't possible together with selecting text in a `markdownarea`. It takes every click itself and gives no `mousedown`, `clicked` or `doubleclicked` events, to itself or to the view holding it; `selectable: false` doesn't apply to it (tested). A transparent view laid over it (a `stack` layout layers its components, the last on top) does get double-clicks, and scrolling still reaches the `markdownarea` through it, but it blocks selecting text and clicking links. Its `doubleclicked` only fires when it also handles `mousedown` (an empty `json` action); without that, inside Alfred the clicks went nowhere (tested).
  - System Events' `keystroke return` doesn't trigger a ↩ shortcut, while a posted Return key event (key code 36) does; ⌘↩ from System Events does.
  - ⌘↩ (Return, key code 36) matches `"⌘↩"`; ⌘ with the keypad's Enter doesn't. Inside Alfred the shortcut runs and the quick view stays open; Alfred doesn't act on the key itself, and the quick view's connection to the pin route isn't followed (tested over ten runs, with an empty `json` action, a script and the real action, in both modes).
- New notes open in Edit mode with the caret in the text. Other notes reopen in the mode their window was last in, kept in the note's sidecar (`mode`): it's recorded when the mode is switched and when the window closes, so a new note written and closed without switching reopens in Edit, as many quick notes will only ever use Edit. A note with no mode, which has never been open in a window (a file added to the notes folder by another app), opens in View. A note pinned from its quick view keeps the view's mode. A blank note always opens in Edit. **Decided**
  - There was an `open_mode` setting for notes without a mode, from when the mode was only recorded on a switch, so every note created and closed in Edit took it. With the mode recorded on close it only covered notes from elsewhere, so it was removed in step 6.
- A pinned window opens at 360×320 (it comes out 32pt shorter, as World Clock records), and can be resized down to 220×160; the quick view is 640×400, which Alfred uses as given, width included. It has a transparent title bar with no visible title, and is dragged by its background. **Decided** for now; sizes may be refined.
- A pinned window's title is the note's title, so pinned notes can be told apart in ⌘-Tab, the Dock and window switchers (it's hidden in the window itself if the title bar is transparent). **Decided**. It's set when the window opens and can't change while it's open: neither an `update` of the window's `id` nor a `window` action with a `title` changed it (tested), and Alfred's docs give the `window` action only `resize`. Renaming a note shows in its window title the next time it's pinned.
- Alfred UI can't keep a window above other apps' windows (see [Alfred requests](../../Alfred%20requests.md#alfred-ui-always-on-top-windows)), so notes behave like normal windows, not floating stickies.

### Saving

- The `textarea`'s `typingstopped` event runs the save script with the text as an argument (`{value:editor.text}`), about a second after typing stops (tested), and the `quit` event saves once more. The actions aren't `async`, so they run one at a time and a `quit` save can't be overtaken by an earlier save. **Decided**
- Both saves happen only while the window's state says Edit (`isEditorText` in `window.js`). `typingstopped` still fires when a switch to View (⌘E or ⌘↩) comes within that second of the last keystroke, when the `textarea` was replaced by the `markdownarea` in step 3, with an empty text, which would blank the note (tested: typing in a pinned window and pressing ⌘↩ straight away blanked the note). With the web view, the hidden `textarea` keeps the text it was last shown with, which ticks may since have changed in the file. **Decided**
- Saves are atomic: the text is written to a hidden temporary file in the same folder, which then replaces the note with `NSFileManager`'s `replaceItemAtURL`, so a crash, a sync app or another save never sees half a note, and when saves race (the `typingstopped` and `quit` saves of one window, each its own process) the last to finish wins whole. `replaceItemAtURL` keeps the note's birth time, permissions and Finder tags; Cocoa's own `writeToFile:atomically:` also swaps in a new file but loses them (tested). A save whose text matches the file is skipped, so its modification time stays. **Decided**
  - Tested by racing separate processes on one note: with versions of about 5 MB (large enough for the writes to overlap despite `osascript`'s startup time), a plain write in place left a mixed note every time, and the atomic save never did. With notes of ordinary size the writes didn't overlap either way, so the risk is small, but the atomic save costs nothing.
- `quit` fires however a window closes (close button, ⌘W, Esc, pinning, and, for the quick view, Alfred closing), but not if its process is killed (see [Multiple windows](#multiple-windows)). In View mode `{value:editor.text}` is the hidden `textarea`'s text, which may be out of date, so the `quit` save goes by the mode in the window's state file and skips saving in View mode, where the file is already up to date from the switch to View and from ticks. **Decided**
- View mode's page is reloaded with the saved text when switching to View. **Decided**
- Text from a note is escaped on its way into a window (see [Placeholders in a note's text](#placeholders-in-a-notes-text)), and unescaped when it comes back to be saved. **Decided**

### Placeholders in a note's text

Alfred UI expands `{var:…}` and `{const:…}` in every string it's given: text in `ui.json`, the window title, and text in `update` and `replace` actions (tested). A name it doesn't know becomes empty, a match can span lines, and matching is case-sensitive (`{VAR:x}` is left alone). In action arguments it also expands `{value:…}` and `{data:…}`. `{file:…}`, `{fileraw:…}`, `{query}` and `{date}` in a component's text aren't expanded. So a note containing `{var:x}` would lose it in its window, and the next save would write the note back without it. Text coming out of a window is safe: a typed `{var:x}` reaches a script through `{value:editor.text}` as typed (tested).

So everything put into a window from a note (its text, title and ID) has a word joiner (U+2060) inserted after the `{` of each `{var:`, `{const:`, `{value:` and `{data:` (`escapeForAlfredUi` in `lib.js`), which stops the match and is invisible. It comes back intact in the editor's text, and `window.js` removes it from exactly those places before saving (`unescapeFromAlfredUi`). **Decided** (tested). The cost, only in notes containing these strings: the caret steps over an invisible character there, and text copied from the editor includes it.

### Changes made elsewhere

- If the file is changed on disk while its window is open (another editor, a sync), and the window has no unsaved typing, the window reloads it. Done with a slow pulse comparing the file's modification time. **Decided**: after the first version. Until then, an edit made elsewhere while a note's window is open is overwritten by that window's next save.
- If the file is deleted or trashed while open, the window closes without its final save, which would otherwise write the note back. ⌥↩ in the results list closes the note's window itself before trashing the file; a deletion by anything else is caught by the same pulse as above, so until that pulse exists such a window stays open. **Decided**

## Multiple windows

One window per note is the main thing to prove before building further.

### Test results

Tested by launching Alfred's UI helper directly with a throwaway bundle, the way Alfred launches an external UI (not yet through the Alfred UI workflow object):

- **Several windows from one bundle work.** Alfred starts a new `Alfred UI.app` process for each launch (`open -n`), with the bundle path as its argument. Two launches of the same bundle gave two independent processes and windows.
- **Each window gets its own variables.** The helper reads the workflow's variables from the `__alfredui_variables` environment variable (a JSON object), but only those declared in `ui.json`'s `variablesconfig` (`{ "note": { "src": "variable", "scriptenv": true } }`). With that, `{var:note}` resolves per window (in the window `id`, `title`, component text and action args), and the UI's scripts get `note` in their environment.
- **Window positions are saved per bundle path, not per window `id`.** With `frameautosave: true`, AppKit saves the frame as `NSWindow Frame <bundle file name>-<SHA-1 of the bundle path>` (e.g. `A-6c9d…` for `…/windows/A.alfredui`) in the `com.runningwithcrayons.Alfred-UI` defaults. The window `id` and `title` don't affect it, and a string `frameautosave` (e.g. `"scratchnote-{var:note}"`) isn't used as a name. So all windows of one bundle share one saved position.
- **A per-note symlink gives each note its own position.** The path isn't resolved before hashing, so launching through a symlink per note (e.g. `<cache>/windows/<note id>.alfredui` → the workflow's bundle) gives each its own saved frame. Two notes dragged to different places and closed reopened exactly where each was left. (With no saved frame under its own name, a window opened once at a frame seeded under `<last part of bundleid>-<same hash>`, so there seems to be a fallback name; it doesn't matter here.)
- **An open note's window can be brought to the front** by its process ID (`NSRunningApplication` … `activateWithOptions`, from JXA). Each window's scripts see their helper's PID as their parent PID, so the `launched` event can record it.
- **`typingstopped` delivers the text.** With `{value:editor.text}` as an action argument, the script gets the whole text, newlines included, after each pause in typing.
- **`quit` fires when the window closes**, by its close button or ⌘W, and `{value:editor.text}` still holds the final text then, so a last save on close works. It doesn't fire when the process is killed.
- **A newly opened window takes keyboard focus** (the helper activates on launch, and the `textarea` has `focus`). Keystrokes meant for another app landed in test windows as they opened. Fine when the user opens a note; something to handle if notes are ever reopened in bulk (e.g. at login).

Then tested through the Alfred UI workflow object (External Trigger → Run Script → Alfred UI, "Launch Externally"):

- **The "Alfred UI file" path takes a placeholder.** `{var:uipath}`, set by the Run Script to the note's symlink, resolved per run, so each note opens through its own path.
- **Each run opens a new window**, in its own process, as with the direct launches.
- **The stream's variables arrive** (declared in `variablesconfig`), and the UI's scripts also get `alfred_workflow_cache` and the other `alfred_*` variables. The stream's argument is passed as an extra launch argument after the bundle path.
- **First-time placement:** with no saved frame, the two windows opened at different, uncentred positions; Alfred seems to place them. Not looked into.
- **"Open within Alfred" runs in Alfred's own process.** With the object's launch mode set to open within Alfred, the same bundle showed in Alfred's window, no helper process started, and the `launched` event's script ran as a child of Alfred itself.

### Limitation: one process per window

Each window is a separate process of Alfred's helper app, and a process has exactly one window: nothing in Alfred UI opens a second window in the same process, or sets how the process appears in ⌘-Tab and the Dock. So every open note is its own entry in ⌘-Tab, named after its window title, rather than one "ScratchNotes" app with several windows. A process can only change its own presentation, and the helper is Alfred's signed app, so a workflow can't change this. The options were:

1. Accept it, and make the entries recognisable: every note window uses the ScratchNotes icon (`iconpath`). The window title is either the note's title (distinguishable in window switchers) or a fixed "ScratchNotes" (consistent, but all alike).
2. One window holding many notes (tabs or a sidebar): one ⌘-Tab entry, but no sticky notes spread around the desktop.
3. A small native app (Swift) launched by the workflow: real multiple windows in one app, and room for things Alfred UI can't do (always on top, reopening notes at login, staying out of ⌘-Tab). Much more code, and a compiled app to build for both architectures, sign and notarise.
4. ### Quick notes and pinned notes

Alfred's own displays (the Text View, "View in Alfred", Quick Look, Large Type) and Alfred UI's "Open within Alfred" mode all live in Alfred's window and process: one at a time, closing when Alfred closes. None stays on the desktop. But the same `.alfredui` bundle can be opened either way, so a note can have two forms. **Decided**:

- **Quick:** ↩ on a note opens it inside Alfred's window, for a quick read or edit. No process, no ⌘-Tab entry; it goes when Alfred closes. The view replaces the results from one frame to the next, with no gap, so it feels part of Alfred (see the tests below and [Seamless quick views](#seamless-quick-views)).
- **Pinned:** ⌘↩ on a note, or Pin (⌘P or its button) in the quick view, opens it as its own window on the desktop (its own process, per-note position, as in [Test results](#test-results)). Pin in the quick view runs `window.js pin`, which saves the editor's text and then prints a `finish` action with the variables `pin_note`, the note's ID, and `pin_mode`, the view's mode, which the pinned window opens in; the quick view's Alfred UI object is connected to the pin route (`open.js pin`, as World Clock's inline view is connected to its detail window), so Alfred carries on there once the view has closed. No AppleEvent is sent, so nothing can deadlock Alfred, and macOS doesn't ask for permission to control Alfred. Pin has to save first: Alfred runs the pin route without waiting for the view's `quit`, so when Pin came within about 0.15 s of the view opening, `open.js` read the note before `quit` had saved it. A new note with text that hadn't been typed in (from a Universal Action, or New note with a query) then opened blank in its pinned window, and closing that window saved the blank text and deleted the note (found in step 6, 25 Nov 2026). This replaces the background `run trigger` tested below.
- If a note is already pinned, ↩ brings its window to the front rather than opening a quick view, so a note is never open in two places at once. Its result says so ("Pinned · …"), and Alfred closes on ↩ with no quick view in between (see [Seamless quick views](#seamless-quick-views)).

Tested so far for the quick form:

- **`quit` fires when Alfred's window closes.** A quick view opened while Alfred was hidden closed at once, and its `quit` event ran with the `textarea`'s text, so a last save on close works. Opening a quick view from outside Alfred (an External Trigger) needs Alfred's window showing first, or it closes straight away.
- **Pinning from the quick view works.** A Pin button whose script fires an External Trigger (→ Run Script → Alfred UI object set to launch externally) and prints `{"finish":{}}` opened the note as its own window.
- **A script running inside Alfred must never wait on Alfred.** The quick view's scripts run synchronously in Alfred's process, so a script that calls Alfred over AppleScript (`run trigger`) and waits for the reply deadlocks Alfred until the AppleEvent times out (2 minutes), with a beach ball and no way to quit Alfred normally. Send the AppleEvent in the background (`… &!`) and return straight away. Killing the stuck `osascript` releases Alfred.
- **A note needs a guard against a second window.** Two queued pins opened two windows for the same note; opening or pinning must check for a live window first (see [Approach](#approach)).

Then tested by hand with a test bundle (a top row of buttons over a `textarea`, opened by a keyword inside Alfred and by an External Trigger externally):

- **The bundle lays out sensibly inside Alfred's window.** The top row and the `textarea` showed at a usable size.
- **Editing inside Alfred works.** Typing, ↩ for a new line, Tab, the arrow keys, ⌘A, ⌘C / ⌘V and ⌘Z / ⇧⌘Z all went to the `textarea`, not to Alfred, and `typingstopped` delivered the text as it does externally.
- **`quit` fires however the quick view closes**: Esc, clicking another app, and pinning (`finish`). Esc in the quick view is handled by Alfred itself: a `⎋` entry in the root view's `shortcuts` doesn't run there, but `quit` does, with the text.
- **Pinning with the background trigger works**, from the quick view and from a pinned window (whose `finish` closes it before the new window launches). Each time the old view's `quit` ran before the new window's `launched`.
- **Esc in a pinned window** (a `⎋` shortcut running a script, then `finish`) runs the shortcut and then fires `quit` with the text.
- **`{value:editor.text}` is empty when the `textarea` isn't in the window.** After the Edit / View toggle has replaced the `textarea` with the `markdownarea`, `quit` (and any other action, including a late `typingstopped` from the old `textarea`) gets an empty string for it. A save must only use it in Edit mode, or it would blank the note (and the empty-note rule would then delete it); see [Saving](#saving).
- **Pinning a note that's already pinned** once opened a second window (above) and once opened none, so the behaviour isn't reliable either way; the guard is still needed.

The gap between the results and the quick view, tested with screen recordings at 60 fps (24 Nov 2026), with temporary keywords whose Script Filter gave one result for a prebuilt bundle:

- **Only a direct connection is seamless.** With the Script Filter connected straight to the Alfred UI object, the results were replaced by the view from one frame to the next: no blank, no fade. Likewise with `stackview`, and with the real note bundle, whose `launched` script (`window.js`) didn't hold the view back.
- **Anything in between makes Alfred hide and fade.** With a Run Script between them, even one that only echoed its input, or a Conditional, Alfred hid its whole window on ↩, search field included, showed nothing for a few frames, and faded the view in over about 170 ms. ScratchNotes' route (Run Script `open.js`, Conditional, Alfred UI) showed nothing for 170–200 ms before the fade; World Clock's inline view (Conditional, Run Script, Alfred UI) for 50–90 ms. `open.js` takes about 50 ms run directly.
- **Filling the view as it opens pops in.** A fixed bundle with an empty content view, filled by a `replace` from its `launched` script, swapped in at once but empty, and its text appeared about 100 ms later.
- So a seamless quick view needs its bundle written, with the note's text, before ↩: by `list.js`. Building and writing a bundle takes about 2–2.5 ms (300 notes: 600–800 ms), so `list.js` could only afford to rewrite the ones that have changed.

#### Seamless quick views

**Decided**, and built (tested in Alfred with a screen recording: the results are replaced by the view from one frame to the next):

- The Script Filter's ↩ connects straight to the quick view's Alfred UI object, and each result's `arg` is its note's quick bundle, `$alfred_workflow_cache/quick/<note id>.alfredui`, which `list.js` writes before the results are shown (`quickWindows` in `lib.js`). ⌘↩ (pin) keeps its Run Script, where a fade doesn't matter.
- A bundle is only rebuilt when its fingerprint changes: a hash of the note's text, its mode, colour and icon, the font size setting, the appearance of the quick view's glyphs (from Alfred's theme; see [Note icons](#note-icons)), the notes and workflow folders, and the modification times of the templates and `lib.js`. The fingerprints are in `quick/.index.json`, read once per run. So most keystrokes rebuild nothing, an edited note's next list rebuilds its bundle, and a changed setting or workflow update rebuilds every bundle once. With 300 notes, `list.js` took 0.16 s a run with nothing to rebuild (0.15 s before quick bundles), and 0.8 s when it rebuilt them all; a bundle took about 2–2.5 ms. With step 5's page (`view.html` and `note.js` too) a run with nothing to rebuild still takes about 0.2 s, most of it reading the notes, and rebuilding them all about 1.5 s (0.85 s before it, measured together on 25 Nov 2026), about 5 ms a bundle: two more atomic writes (about 0.7 ms) and reading `ui/view.html` and `ui/view.js` again for each bundle (about 0.4 ms), as the JSON templates are. Reading the templates once per run would save about 0.2 s of a full rebuild; not done, as a full rebuild only follows a workflow update or a change of setting, and the "Loading notes..." subtext covers it. Variables and the bundle folder are read once per run: reading them per note through the ObjC bridge added 0.1 s.
- Each run also removes the quick bundles of notes that have gone, and of New notes offered earlier and never opened, keeping any that's open (has a window state). Bundles for new notes that `new.js` offered and that weren't opened are removed by `list.js`'s next run.
- New note: `list.js` picks the new note's ID (the time) and writes its bundle with the query as its text, each time it shows the result; within the same second it's the same ID and bundle. A quick bundle alone doesn't make an ID taken (`isNoteIdInUse`), so these don't pile up as -2, -3….
- The view's `launched` (`window.js`) compares the note with the hash of the text its bundle was built with (`textHash` in `context.json`), and if the note has changed since (an edit elsewhere between the list and ↩), gives the window the note as it is, so a stale text can never be saved back over it: an `update` of the `textarea`'s text in Edit, or a reload of the page in View.
- A note that's already pinned (`pinnedNoteIds`, from the state folder) gets a result with no arg and the variables `pinned` = `1` and `pin_note` = its ID. The Script Filter's ↩ has a second connection, beside the one to the Alfred UI object, to a Conditional that goes on only when `pinned` is `1`, to the pin route, where `open.js` brings the pinned window to the front. The Alfred UI object, given an empty path, shows nothing. Seen in a recording (24 Nov 2026): on ↩ the results go from one frame to the next, with no quick view and no error, and the pinned window comes to the front; and the second connection doesn't affect other notes, whose view still replaces the results seamlessly. Not covered by `dev/test-list.sh`, which can't fake a live Alfred UI helper.
- If a note is pinned after its results were listed, its quick view still opens, and hands over: its `launched` finishes as Pin does, with `pin_note`, so Alfred carries on to the pin route. The view doesn't record a state, and its `quit` sees the pinned window's state (the other form) and leaves everything alone. Seen in a recording: the quick view shows for about 130 ms, then Alfred closes and the pinned window comes to the front.

### Per-window state

Variable persistence (`persist`) is keyed on the UI's `bundleid`, so all windows would share it. Each window's own state (its form, PID and mode) is in a file keyed by note ID in `$alfred_workflow_cache/state/` instead (see [The note window bundle](#the-note-window-bundle)).

### Approach

**Decided**, and built in step 3 (details in [The note window bundle](#the-note-window-bundle)):

- Each note opens from its own bundle: `$alfred_workflow_cache/quick/<note id>.alfredui` for a quick view, written by `list.js` (see [Seamless quick views](#seamless-quick-views)), and `$alfred_workflow_cache/windows/<note id>.alfredui` when pinned, so a pinned window reopens where it was left. A pinned bundle is a throwaway cache folder, rewritten on every pin, and kept after the window closes only so its path, and so the window's saved position, stays the same. Both are deleted when their note is: deleted on close for being empty, or moved to the Trash.
- On `launched`, the window records its form, PID and mode in a state file keyed by note ID; on `quit` it removes it. Opening a note that has a live pinned window brings that window to the front instead of opening a second one (tested, from ↩ and ⌘↩).

## Language

**Decided**: JavaScript for Automation (JXA) for all scripts, as one executable script per job (or one script with subcommands), run as external script files with an `osascript -l JavaScript` shebang.

- JSON is native, both for Script Filter output and for Alfred UI's `update` / `replace` actions.
- Unicode-safe string handling for titles, previews and truncation, and easy relative dates.
- Cocoa through the ObjC bridge where needed: atomic writes (`replaceItemAtURL`), file attributes (modification and birth dates), the Trash via Finder for "Put Back".
- Ships with macOS on every version Alfred 6 supports, with nothing to vendor or sign.
- Cost: about 70ms to start `osascript`, which is fine for a Script Filter, a save, or a pulse every few seconds. JXA has no `require`, so every script loads the shared `lib.js` and evaluates it at startup (see [Loading lib.js](#loading-libjs)).

Alternatives considered: zsh with `jq` (Now Playing's approach) is quick to start, but Markdown title parsing, Unicode truncation and JSON building are clumsier, and `/usr/bin/jq` only ships from macOS 15. Swift would need compiled, signed and notarised binaries. Python no longer ships with macOS.

### Loading lib.js

**Decided**, and tested. JXA has no `require`, and `Library()` only loads from `~/Library/Script Libraries`, which a workflow can't ship in. So each script ends with this function, and calls `loadLib(argv, "lib.js")` first thing in `run`:

```js
function loadLib(argv, relativePath) {
  const args = ObjC.deepUnwrap($.NSProcessInfo.processInfo.arguments);
  let script = args[args.length - argv.length - 1];
  if (!script.startsWith("/")) script = `${$.NSFileManager.defaultManager.currentDirectoryPath.js}/${script}`;
  const path = $(script).stringByDeletingLastPathComponent.stringByAppendingPathComponent(relativePath).stringByStandardizingPath.js;
  const source = $.NSString.stringWithContentsOfFileEncodingError(path, $.NSUTF8StringEncoding, null);
  if (source.isNil()) throw new Error(`Can't load ${path}`);
  (0, eval)(source.js);
  return path;
}
```

- `lib.js` is found from the script's own path, not the working directory, so it loads whoever runs the script and from wherever: an external script (Alfred), an Alfred UI action running `scripts/window.js` by its absolute path, or a terminal. A script run through its shebang or as `osascript -l JavaScript <path>` gets `osascript`'s arguments with its own path just before `argv`, which is what `run` receives; a relative path is from the working directory. `dev/test-storage.sh` runs a script with this function by absolute and relative paths, from other folders (including `/`), through a symlinked workflow folder (as Alfred links it) and with `osascript -l JavaScript <path>`.
- The indirect `eval` (`(0, eval)(…)`) runs `lib.js` in the global scope: its function declarations become globals, while its top-level `const` and `let` stay private to it (its functions still see them). It mustn't have `"use strict"`, which would keep the functions private too. All functions share one namespace, so `lib.js` names them for what they do (`noteSummary`, not `summary`), and a script mustn't define a function with the same name as one of its functions.
- `lib.js` mustn't use regular expression lookbehind (`(?<=…)`, `(?<!…)`): macOS 12's JavaScriptCore can't parse it, and a syntax error stops the whole file loading.

### lib.js

The storage functions (step 1), for the later scripts. Fuller notes are in the comments in `lib.js`.

- `notesFolder()`: the notes folder (see [Notes folder](#notes-folder)). The default folder is created if missing; a configured folder must exist. Throws if `notes_folder` and `alfred_workflow_data` are both unset (a script run by hand needs one of them).
- Moving the notes folder (see [Moving the notes folder](#moving-the-notes-folder)): `checkNotesFolderMove()`, called first by `list.js`, `new.js` and `open.js`, returns whether the notes are ready, moving or failed to move, and starts `move.js` when they have to move; `notesFolderMoveOutput()` and `notesFolderErrorItem()` are the Script Filters' results for a move and for a folder that can't be opened; `moveNotes(from, to)` moves the notes; and the record of the last folder, the lock and the failure record have functions of their own.
- `errorText(error)`: an NSError out-parameter's description. Pass `$()` as the parameter: an NSError read back from a `Ref()` crashes `osascript` (tested on `moveItemAtPath` and `copyItemAtPath`).
- `noteStore(folder = notesFolder())` returns the functions for the notes in a folder. Notes are passed as IDs, which are checked (`isNoteId`: one non-hidden filename component, so an ID from a script argument can't reach outside the folder):
  - `list()`: every note, last edited first, as note objects: `{ id, path, fileName, text, meta, modified, created, title, preview }`. `text` is the whole file, `meta` the sidecar's object (`{}` without one), `modified` and `created` are `Date`s. For the results list. Gives notes without a sidecar one (see [Metadata](#metadata)), as `read` does.
  - `read(id)`: one note object, or null if it doesn't exist.
  - `newId({ date, isTaken })`: an ID for a new note. Nothing is written, so a new note can open before it's saved; `isTaken(id)` should return true for the IDs of notes that are open but not saved yet (in step 3, ones with a window bundle or state file), or two notes created in the same second would get the same ID.
  - `save(id, text)`: saves the whole text atomically and returns `"created"`, `"saved"`, `"unchanged"` (not rewritten) or `"blank"` (a new note with blank text, not written). Records `created` in the sidecar on a note's first save.
  - `readMeta(id)` and `updateMeta(id, changes)`: the sidecar. `updateMeta` merges, removes keys set to null, and returns the result. It works for a note that isn't saved yet (a colour picked before typing).
  - `deleteIfEmpty(id)`: for a window closing on its note. Deletes the note and its sidecar if its text is blank or it was never saved, and returns whether it did.
  - `trash(id)`: moves the note to the Trash through Finder, keeping its sidecar, and returns its path in the Trash (null if there was no note). macOS asks once for permission to control Finder: for Alfred, the first time a note is trashed.
  - Also `notePath(id)`, `exists(id)` and `folder`.

- The palette (step 4): `notePalette()`, `notePaletteColour(name)` (a colour by name, or null), `noteColour(meta)` (a note's colour: its own, or the `default_colour` setting's, or yellow) and `noteDefaultColour()`. A colour is `{ name, label, heart, tint, spine, control }`. `noteColourAction` builds the action of a colour's menu item and shortcut. `updateNoteContext(id, form, changes)` merges changes into a bundle's `context.json`.
- Window state: `readNoteState(id)`, `writeNoteState(id, state)`, `removeNoteState(id)`, `pinnedNotePid(id)` (the PID of a live pinned window, checked to be an Alfred UI helper, or null), `pinnedNoteIds()` (the IDs of the notes with a live pinned window, for `list.js`), `activateWindowProcess(pid)`, `closePinnedNoteWindow(id)` (force-quits the process, so its `quit` doesn't run, for `trash.js`), and `isNoteIdInUse(id)`, the `isTaken` for `newId` (a pinned bundle or state file exists).
- `runningApp(pid)` imports AppKit only when it's needed, so scripts that don't use it don't pay for loading it.
- Top-level `const`s are private to `lib.js` (see [Loading lib.js](#loading-libjs)), so a value a script needs, such as the palette, comes from a function.

Learned while building it:

- An ObjC method's object parameter must be given `$()` for nil: JavaScript `null` arrives as `NSNull`, which crashed `replaceItemAtURL` (as its backup name). `null` is fine for `NSError **` and other out parameters.
- `list()` of 300 notes took about 115 ms, on top of `osascript`'s startup, and about 270 ms the first time, when it writes their sidecars.
- The Trash test confirms Finder moves the note to the Trash; that Finder's "Put Back" then works isn't checked automatically, since the Trash's records can't be read without Full Disk Access.

### The note window bundle

**Decided**, and built in step 3. Each note opens from its own generated bundle: `$alfred_workflow_cache/quick/<note id>.alfredui` for a quick view, whose `ui.json` `list.js` writes when it's out of date (see [Seamless quick views](#seamless-quick-views)), and `$alfred_workflow_cache/windows/<note id>.alfredui` for a pinned window, which `open.js` writes every time the note is pinned. The separate folders keep `list.js` from ever rewriting an open pinned window's bundle. Generated bundles replace the tested arrangement of a symlink per note to one shared bundle, with the note passed in variables:

- Some window settings need real JSON types (the font size is a number), and variables reach a UI only as strings, which Alfred ignores in those places (see Now Playing's `DEVELOPMENT.md`). A `{file:…}` placeholder could insert typed JSON, but its path can't contain a placeholder, so it can't be per note.
- Each note still has its own bundle path, so each pinned window still keeps its own saved position: the frame is saved under a hash of the path, whether the path is a symlink or a folder.
- `writeNoteWindow` builds `ui.json` from the templates in `ui/` with the note's text, the window `title` (the note's title), the note's colour, the font size, the form and the mode (`noteWindowUi` in `lib.js`). Text, title and ID are escaped (see [Placeholders in a note's text](#placeholders-in-a-notes-text)).
- It also writes `context.json` into the bundle: the notes folder, font size and the note's colour's name, which the window's scripts need but don't get from Alfred (they only get the `alfred_*` variables), so `window.js` can save to the right folder and give the window parts that match, and `textHash`, a hash of the text the window opens with, for `launched`'s check for a changed note, then of the text its page was last given, for `tick`'s. And it writes the page, `view.html` and `note.js` (see [View mode in a web view](#view-mode-in-a-web-view)).
- The bundle's actions run `scripts/window.js` by its absolute path, with the note ID and the form as arguments; the form says which bundle the window opened from.
- Both Alfred UI objects take the bundle path as `{query}`: the result's arg for the quick view, `open.js`'s for the pinned window.

The templates are `ui.json` as Alfred UI reads it, with a few directives that `resolveNoteTemplate` resolves and removes, so one set of files covers both forms and both modes:

- `"@form": "quick"` or `"pinned"` on an array element keeps it in that form only (the Pin button and ⌘P are quick only, the `⎋` shortcut pinned only); `"@mode": "edit"` or `"view"` likewise.
- `"@quick"`, `"@pinned"`, `"@edit"` and `"@view"` hold properties merged into their object in that form or mode (the quick view's size and insets, the toggle button's symbol and tooltip).
- A whole string that's a token (`"@note"`, `"@text"`, `"@title"`, `"@tint"`, `"@colourDot"`, `"@colourShortcuts"`, `"@fontSize"`, `"@form"`, `"@mode"`, `"@iconPath"`, `"@iconImage"`, `"@glyph:<name>"`, `"@dropdowns"`, and the layout tokens from `NOTE_WINDOW_LAYOUT`; see `noteWindowTokens`) becomes its value, typed (the font size is a number, a place an object), except in `args`, where it's a string. An array element that's a token whose value is an array is replaced by its elements: `window.json`'s shortcuts end with `"@colourShortcuts"`, ⌘1 to ⌘6, and `content.json`'s components with `"@dropdowns"`, the catcher and the two pickers.
- An action's `"src": "scripts/…"` becomes an absolute path, since the bundle isn't in the workflow folder.
- `window.json`'s root view has `{ "id": "content" }`, `{ "id": "customise" }` and `{ "id": "actions" }` placeholders, filled with the template of the same name (`NOTE_WINDOW_PARTS`). The colour and icon changes replace the `customise` group.

Each window's state is in `$alfred_workflow_cache/state/<note id>.json`: its form (`quick` or `pinned`), PID and mode (`edit` or `view`). `launched` writes it (the PID is `window.js`'s parent: the helper's when pinned, Alfred's when quick), the toggle updates the mode, and `quit` removes it. A note counts as pinned only when the form is `pinned` and the PID is still an Alfred UI helper (`pinnedNotePid`); the quick view's PID is Alfred's own, which is always alive. A `quit` without a state (its `launched` failed) saves only non-blank text, since blank text could be View mode's empty value.

The objects: the Script Filter's ↩ goes straight to the quick view's Alfred UI object (open within Alfred), with the result's quick bundle as its path, and also to a Conditional that goes on to the pin route's Run Script only when the variable `pinned` is `1` (a pinned note's result). ⌘↩ runs `./scripts/open.js pin "$1"`, an inline zsh one-liner (an external script can't be given a fixed first argument), then a Conditional that goes on only when the variable `open_window` is `1` (`open.js` leaves it empty when it brought a pinned window to the front instead), then the pinned window's Alfred UI object (launch externally). The quick view's Alfred UI object is connected to the pin route's Run Script, for Pin. The plan's External Trigger `pin` isn't needed for that, so there isn't one; step 6's routes into the pin route (the hotkey, and ⌘↩ on the new-note keyword's results) connect to its Run Script directly.

#### Alfred UI findings from step 3

- `root` goes inside `window` in `ui.json`. At the top level, the helper creates a window but never shows it.
- The root view's `events` take `launched` and `quit`; a top-level `events` key doesn't fire.
- A view's `padding` is a single number; an object is ignored. Per-side spacing is `insets` in a child's `constraints`.
- A vertical `inline` root doesn't fill the window: it centres its contents. A `border` root fills it, but a `top` region needs an explicit `size: { height }`, or it collapses to the window's top edge.
- `markdownarea` spacing keys (see [Components](#components)); the `markdownarea` was replaced by a web view in step 5.
- Launching the helper directly (`open -n … --args <bundle>`), even with Alfred's `__alfredui_constants` and `__alfredui_variables` in the environment, didn't show a window this time, though it did in the earlier tests; going through an Alfred UI object works.
- `alfred://runtrigger/<bundle id>/<trigger>/?argument=…` runs an External Trigger (with `availableviaurlhandler`), without an AppleEvent. Not used.
